# Naru v2 — 기능 정리와 화면 재설계

상태: **진행 중 (M7-3 진행 중)** · 제안 2026-10-04 · 갱신 2026-10-10 · 이름을 Shelf에서 Naru로 바꿨다
관련: [웹서버 엔진을 Caddy로](caddy-engine.md) · [Caddy 사용성 분석](caddy-usability.md)

## 0. 무엇을 하나

세 가지를 한 번에 한다.

1. **백엔드를 Go로.** 화면은 지금처럼 서버가 완성해서 보낸다 (Go 템플릿).
2. **웹서버 엔진을 Caddy로.** 공식 이미지 + Shelf 모듈, 컨테이너는 따로.
3. **기능을 다시 정리하고 화면과 사용 흐름을 새로 설계한다.**

한 번에 하는 이유: 화면을 어차피 Go로 다시 그린다. 옛 화면을 그대로 옮긴 뒤 또 고치면 두 번 일하게 된다.

| 운영 | 6 | 1 (빌드 이미지 정리) |

화면 메뉴는 `Dashboard · Apps · Proxy · Notifications · System · Settings` 여섯 개다.

### 1.2 실제로 겪은 불편

v2의 근거는 추측이 아니라 실서버를 운영하며 실제로 부딪힌 일들이다.

| # | 무슨 일이 있었나 | 구조적인 원인 |
|---|---|---|
| 1 | 앱을 등록했는데 **502**. 컨테이너는 healthy인데 실제로는 다른 포트를 듣고 있었다 | Shelf는 앱 설정과 프록시를 둘 다 알면서 **서로 대조하지 않는다** |
| 2 | Shelf **자기 자신**이 앱으로 배포됐다 | 저장소 주소를 확인하지 않는다 |
| 3 | Docker 소켓을 못 잡았는데 화면은 멀쩡했다 | 경고가 로그 한 줄뿐이다 |
| 4 | 비밀번호를 **두 번** 잊었고 매번 SSH로 들어가야 했다 | 화면에 비밀번호 변경이 없다 |
| 5 | HTTPS를 하려면 Apps에서 도메인을 적고, Proxy → SSL로 가서 따로 발급해야 했다 | 한 가지 일이 **여러 화면에 흩어져** 있다 |
| 6 | 도메인을 Apps에서도 Proxy에서도 정한다. 관리 도메인을 앱이 덮어쓸 수 있다 | **같은 것을 두 주인**이 관리한다 |
| 7 | "Open" 버튼이 `http://localhost:포트`를 연다 — 실서버에서는 내 컴퓨터를 연다 | 링크를 실제 주소로 만들지 않는다 |
| 8 | 새 앱 폼에 입력 칸이 **12개** 한꺼번에 나온다 (호스트 포트·볼륨·빌드 경로 포함) | 자주 쓰는 것과 드물게 쓰는 것을 나누지 않았다 |
| 9 | 설정 화면은 읽기 전용 두 줄, 시스템 화면은 Node 프로세스 정보(PID 등) | 사용자에게 의미 없는 정보를 보여준다 |
| 10 | 웹훅 주소·시크릿을 GitHub에 직접 복사해 넣었다 | 연결 상태를 Shelf가 모른다 (들어왔는지 확인할 방법이 없음) |
| 11 | 화면 라벨은 영어(Apps, Deploy), 설명은 한국어 | 화면 언어를 정한 적이 없다 |

### 1.3 정리 결정

| 지금 | v2 | 이유 |
|---|---|---|
| Apps + Proxy (도메인 두 곳) | **서비스 하나로 합침** | #5, #6 |
| SSL 화면에서 발급 클릭 | 도메인을 적으면 자동 (Caddy) | #5 |
| 전체 배포 목록 화면 | 서비스 상세의 배포 탭 + 홈의 최근 활동 | 따로 볼 일이 드묾 |
| 접근 로그 화면 (Proxy 아래) | 서비스 상세의 로그 탭 | 로그는 서비스 단위로 본다 |
| 시스템 화면 (Node 정보) | **서버** 화면 — 호스트·Docker·Caddy·인증서 전체 | #3, #9 |

| 앱 가이드 화면 | 서비스 추가 흐름 안의 도움말 | 필요한 순간에 보여줌 |
| 알림 | 그대로 | — |
| 새 앱 폼 12칸 | **3단계** + 고급 접기 | #8 |

## 2. 새 모델 — "서비스" 하나

지금은 **앱**(Apps)과 **프록시 호스트**(Proxy)라는 두 주인이 도메인을 나눠 가진다.
v2에서는 **서비스**가 유일한 단위다. 서비스는 "도메인으로 들어오는 무언가"다.

| 종류 | 뜻 | 지금의 무엇 |
|---|---|---|
| **저장소** | Git 저장소를 빌드해서 실행 | Git 앱 |
| **이미지** | Docker 이미지를 받아 실행 | 이미지 앱 |
| **외부 연결** | 이미 떠 있는 것으로 보냄 (다른 컨테이너, 서버의 프로그램, 다른 서버) | 손으로 만든 프록시 호스트 |
| 정적 사이트 *(선택)* | Caddy가 파일을 직접 서빙 — Dockerfile 불필요 | 없음 (새로) |

모든 서비스가 같은 네 부분으로 되어 있다:

```
서비스
├─ 어디서 오나       소스 — 저장소 / 이미지 / 외부 주소
├─ 어디로 들어오나   도메인 · HTTPS
├─ 어떻게 서빙하나   웹서버 설정 (Caddy)
└─ 어떻게 지켜보나   상태 · 로그 · 알림
```

관리 도메인은 서비스가 아니다. 설정에서 따로 정하고, 서비스가 그 도메인을 쓰려고 하면 막는다 (#6).

## 3. 화면 구조

### 3.1 메뉴

| 지금 | v2 |
|---|---|
| Dashboard | **홈** — 서버 상태 + 주의가 필요한 것 |
| Apps | **서비스** |
| Proxy | (서비스에 합쳐짐) |
| Notifications | **알림** |
| System | **서버** — 호스트 · Docker · Caddy · 인증서 전체 |
| Settings | **설정** — 계정 · 관리 도메인 · 기본값 |

여섯 개가 다섯 개로 줄고, 같은 일을 두 곳에서 하는 메뉴가 사라진다.

### 3.2 홈 — 문제가 먼저 보인다

```
┌──────────────────────────────────────────────────────────────┐
│  주의가 필요한 것 (2)                                          │
│  ● blog       502 — 앱이 4023이 아니라 81을 듣고 있습니다  [고치기] │
│  ● docs.…     HTTPS 발급 실패 — DNS가 이 서버를 가리키지 않습니다    │
├──────────────────────────────────────────────────────────────┤
│  CPU 12% · 메모리 2.1/7.7GB · 디스크 여유 40GB · Caddy 정상     │
├──────────────────────────────────────────────────────────────┤
│  서비스 5          최근 활동                                    │
│  ● blog            14:02 docs 배포 성공 (a1b2c3d)              │
│  ● docs            13:40 blog 다운 → 13:41 복구                 │
│  ● landing         …                                           │
└──────────────────────────────────────────────────────────────┘
```

아무 문제가 없으면 맨 위 칸은 "모두 정상"으로 접힌다.

### 3.3 서비스 상세 — 한 서비스의 모든 것이 한 곳에

```
blog  ● 정상   https://blog.example.com ↗                  [배포] [중지]
──────────────────────────────────────────────────────────────────
개요 │ 배포 │ 도메인·HTTPS │ 웹서버 │ 로그 │ 설정
```

| 탭 | 들어 있는 것 |
|---|---|
| 개요 | 상태, 주소, 최근 배포, CPU·메모리, 문제가 있으면 원인과 해결 버튼 |
| 배포 | 배포 이력·로그·롤백, 웹훅 연결 (마지막으로 받은 시각까지) |
| 도메인·HTTPS | 도메인 목록, 인증서 상태(발급 중·완료·실패와 원인), HTTPS 강제, HSTS |
| 웹서버 | 헤더 · IP 제한 · 비밀번호(기본 인증) · 점검 중 · 경로별 연결 · 고급(Caddyfile) · nginx 설정 가져오기. 압축은 칸 없이 늘 켬 (캐시·CORS·에러 페이지는 앱이 하는 일로 둔다) |
| 로그 | 컨테이너 로그 + 접근 로그 (한 화면에서 시간순) |
| 설정 | 소스, 환경변수, 볼륨, 포트, 삭제 |

"Open" 링크는 서비스의 **실제 도메인**으로 연다 (#7).

### 3.4 서비스 추가 — 세 단계

```
1. 무엇을        ○ 저장소   ○ 이미지   ○ 외부 연결   ○ 정적 사이트
2. 어디서        https://github.com/me/blog.git
                 포트 3000  ← 이미지가 열어둔 포트에서 자동으로 채움
3. 어디로        blog.example.com   ✓ 이 서버를 가리킵니다
                                     (아니면: ✗ DNS가 1.2.3.4를 가리킵니다)
                 ▸ 고급  브랜치 · 빌드 경로 · 토큰 · 환경변수 · 볼륨 · 호스트 포트

                                                     [만들고 배포하기]
```

- 포트는 이미지의 `EXPOSE`에서 **자동으로 채운다.** #1의 502는 대부분 여기서 막힌다.
- 도메인은 입력하는 순간 DNS를 확인한다. HTTPS가 실패할지 미리 안다.
- 자주 안 쓰는 칸은 "고급"에 접어둔다 (#8).
- 저장소가 Shelf 자신이면 경고한다 (#2). 관리 도메인이면 막는다 (#6).

만들면 배포 진행 화면으로 넘어가고, 끝나면 HTTPS가 자동으로 붙는다. SSL 화면으로 갈 일이 없다.

## 4. UX 원칙

각 원칙은 1.2의 실제 사건에서 나왔다.

| 원칙 | 뜻 | 근거 |
|---|---|---|
| **문제가 먼저 보인다** | 홈 맨 위는 "주의가 필요한 것" | #1, #3 |
| **한 곳에서 끝난다** | 서비스 하나에 관한 일은 그 서비스 화면 안에서 | #5, #6, #10 |
| **실패는 원인과 해결을 말한다** | "502"가 아니라 "앱이 81을 듣고 있습니다 [포트를 81로 바꾸기]" | #1, #3 |
| **위험한 건 미리 막는다** | 관리 도메인 중복, 자기 자신 배포, 포트 충돌 | #2, #6 |
| **기본값으로 충분하다** | 고급은 접어두고, 자동으로 알 수 있는 건 자동으로 | #8 |
| **서버에 들어가지 않아도 된다** | 비밀번호 변경, 로그, 진단을 전부 화면에서 | #4 |
| **링크는 실제 주소로** | localhost가 아니라 서비스의 도메인 | #7 |

### Shelf만 할 수 있는 진단

앱 설정과 프록시를 둘 다 알기 때문에 가능한 것들. v2의 차별점이다.

| 진단 | 어떻게 아나 |
|---|---|
| 앱이 다른 포트를 듣고 있다 | 컨테이너 포트로 접속해보고, 실패하면 이미지가 열어둔 포트와 비교 |
| DNS가 이 서버를 가리키지 않는다 | 도메인을 조회해 서버 공인 IP와 비교 |
| 웹훅이 한 번도 안 들어왔다 | 서비스별 마지막 수신 시각 기록 |
| Docker·Caddy에 연결할 수 없다 | 홈 맨 위에 표시, 해결 방법(소켓 경로 등) 함께 |

## 5. 기술 구조

### 5.1 바이너리 둘, 저장소 하나

```
shelf/
├─ cmd/shelf/          관제 (Go) — 화면, API, 배포, 감시, 알림
├─ internal/
│  ├─ app/             조립·수명주기 (지금의 kernel)
│  ├─ service/         서비스 모델, 저장소, 배포 파이프라인
│  ├─ engine/          Caddy 설정 번역기, 관리 소켓, 인증서 장부
│  ├─ docker/          Docker Engine API (소켓으로 직접)
│  ├─ watch/           감시, 지표, 진단
│  ├─ notify/          알림
│  ├─ auth/            계정, 세션
│  └─ web/             핸들러, 템플릿(html/template), 정적 파일
├─ caddy-shelf/        Caddy에 끼울 모듈 (Go) — 인증서 상태 API, 이벤트
├─ migrations/         SQL
└─ docs/
```

컨테이너는 둘 — `shelf`(관제)와 `caddy`(공식 이미지 + Shelf 모듈). Caddy를 Shelf 프로세스 안에 넣지 않는다. Shelf가 죽어도 사이트는 산다.

### 5.2 고르는 것과 이유

| 무엇 | 고른 것 | 이유 |
|---|---|---|
| HTTP·라우팅 | 표준 라이브러리 `net/http` | Go 1.22부터 경로 패턴 라우팅이 표준에 있음. 의존성 0 |
| 화면 | `html/template` | 출력 자동 이스케이프 — 지금 엘리먼트 빌더가 하던 일을 언어가 해준다 |
| 브라우저 동작 | 지금의 런타임 JS 그대로 | HTML 속성(`data-act` 등)만 보고 움직이므로 백엔드 언어와 무관 |
| DB | SQLite, 순수 Go 드라이버 | C 컴파일러 없이 빌드 — 서버 종류(amd64·arm64)마다 빌드가 쉽다 |
| Docker | Engine API를 소켓으로 직접 | 필요한 엔드포인트만 — 공식 SDK는 의존성이 크다. 지금의 CLI 호출(1회 40ms)보다 빠르다 |
| 인증서 | 없음 | Caddy가 한다 |
| 빌드 | Docker 안에서 (`golang` 이미지) | 로컬에 Go를 설치하지 않아도 된다 |

런타임 의존성을 지금처럼 적게 유지한다 — 목표는 SQLite 드라이버와 Caddy 모듈용 Caddy 패키지 정도.

### 5.3 지금 만든 것 중 가져가는 것

| 가져감 | 형태 |
|---|---|
| 문서 (SPEC · OBJECTS · PROCESS · HISTORY) | v2 기준으로 갱신. "명세 → 책임 → 구현 → 테스트" 순서는 그대로 |
| 아키텍처 테스트의 규칙 | Go 테스트로 다시 — 시스템 간 직접 참조 금지, SQL은 저장소 계층에만, 문서에 없는 타입 금지 |
| 브라우저 런타임 JS (221줄) | 파일 그대로 |
| CSS · 아이콘 · 디자인 토큰 | 다듬어서 |
| API 응답 규칙 (`{ok, data}` · 오류 코드) | 그대로 |
| 이번 세션에서 찾은 불변식들 | Caddy 관리 소켓, HTTPS 강제 조건, 웹훅 HMAC, 고아 세션 차단 등 — 테스트와 함께 |

## 6. 데이터 이전

### 6.1 원칙

**v1 DB는 건드리지 않는다.** v2는 처음 뜰 때 v1 DB를 읽어 **새 파일**(`data/shelf.db`)로 옮긴다. 문제가 생기면 v1 이미지를 다시 띄우면 그대로 돌아간다.

### 6.2 무엇이 어디로

| v1 | v2 |
|---|---|
| 앱(projects) | 서비스 (저장소·이미지) |
| 앱이 만든 프록시 호스트 | 그 서비스의 도메인으로 합쳐짐 |
| 손으로 만든 프록시 호스트 | 서비스 (외부 연결) |
| 관리 도메인 프록시 호스트 | 설정의 관리 도메인 |
| 인증서 | Caddy가 새로 발급. 업로드한 것은 파일로 옮김 |
| 계정·세션 | 그대로 — **비밀번호를 다시 정할 필요 없음** |
| 알림 채널·발송 기록 | 그대로 |
| 배포 이력 | 그대로 |

### 6.3 반드시 맞춰야 하는 것

- **비밀번호 해시.** v1은 `scrypt(비밀번호, salt를 hex 문자열 그대로, N=16384·r=8·p=1, 64바이트)`로 저장했다. Go에서 같은 계산으로 검증해야 기존 계정이 살아남는다 — 테스트로 고정한다.
- **컨테이너 이름.** 지금 돌고 있는 앱은 `shelf-{이름}`이다. v2도 같은 규칙으로 찾아야 앱을 재시작하지 않고 넘겨받는다. 이름을 바꾸는 건(프로젝트 이름 변경 포함) 별도 단계로 한다.

## 7. 단계

각 단계는 **님 서버에서 눈으로 확인할 수 있는 것**으로 끝난다.

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| **M0** | 이 문서 확정 + 화면 시안 | 시안을 보고 방향 합의 |
| **M1** | Go 골격 · 첫 실행 설정 마법사 · 로그인 · 홈 · 설정(비밀번호·관리 주소) · v1 DB 읽기 | 기존 계정으로 v2에 로그인, 화면에서 비밀번호 변경. `.env` 없이 첫 설정 |
| **M2** | 서비스 목록·상세(읽기) + Caddy 연결 | 기존 앱들이 v2 화면에 보이고 Caddy로 서빙됨 |
| **M3** | 서비스 추가·배포·웹훅·롤백 | 새 흐름 3단계로 앱 하나 올리기 |
| **M4** | HTTPS 자동 · 인증서 상태 · Caddy Shelf 모듈 | 도메인만 적으면 HTTPS |
| **M5** | 서비스마다 웹서버 설정 — 헤더 · IP 제한 · 비밀번호(기본 인증) · 점검 중 · 경로별 연결 · 고급(Caddyfile) · nginx 설정 가져오기. 압축은 늘 켬 | 화면에서 켜면 실제 응답이 바뀌고, 틀린 설정은 웹서버에 닿기 전에 되돌려짐 |
| **M5.5** | 설치 방식 두 가지 — Docker(compose)와 설치형(systemd). 같은 바이너리, `NARU_INSTALL=docker\|host` | 설치형으로 깐 Naru에서 배포가 끊김 없이 되고, 컨테이너가 재시작해 IP가 바뀌어도 따라감 |
| **M6** | 감시·알림·진단 — 알림 채널과 상태 변화 알림, 진단(포트·DNS·웹훅·Docker/Caddy), 로그 탭(컨테이너 + 접근 로그), 홈 "주의가 필요한 것", 서비스 CPU·메모리 | 포트 불일치가 홈에 원인과 함께 뜸 |
| **M7** | 실서버 전환 · v1 코드 정리 | 님 서버가 v2로 돌고, v1 이미지로 되돌리기 리허설 완료 |

개발은 님 서버 데이터의 **복사본**으로 로컬에서 한다. 실서버는 M7까지 v1 그대로 돈다.

## 8. 정한 것

1. **화면 언어** — 한국어·영어 둘 다. 브라우저가 한국어면 한국어, 아니면 영어. 화면에서 전환.
2. **이름** — Naru. 바이너리·모듈·쿠키·DB 파일은 `naru`. 단, 운영 중인 v1 앱 컨테이너(`shelf-*`)와 네트워크(`shelf-net`)는 이름을 그대로 넘겨받는다 — 새로 만드는 것부터 `naru-*`.
3. **정적 사이트** — 넣는다. 컨테이너 없이 웹서버가 파일을 직접 서빙.
4. **화면 시안** — 확인함. 메뉴는 서비스 · 로그 · 설정.
5. **`.env` 대신 첫 실행 마법사** — 계정 → 관리 화면 주소(DNS 확인) → HTTPS 연락처. 설정 주소는 서버 로그에만 찍히는 토큰으로 연다 — 로그를 볼 수 있는 사람만 관리자를 만들 수 있다. `ADMIN_DOMAIN`·`ACME_EMAIL` 환경 변수가 있으면 화면보다 우선한다.
6. **인증서 실패 이유는 해석하지 않는다** (2026-10-10) — Caddy는 실패를 로그에만 남긴다(Pebble로 실측). 화면은 "인증서 받는 중"과 Naru가 직접 본 DNS로 충분하고, 원문은 로그에서 본다. 로그 문구를 분류하면 틀린 안내가 될 수 있다.
7. **주소의 HTTPS·HSTS 바꾸기 칸은 두지 않는다** — 바꾸려면 주소를 떼고 다시 붙인다. v1에서 온 HSTS는 그대로 지킨다.
8. **M5 범위** — 위 단계표대로. 압축은 칸 없이 늘 켠다. 경로별 연결의 대상은 다른 서비스나 외부 주소.
9. **설치 방식 두 가지** (2026-10-10) — Docker로 올리면 Naru가 Docker 밖(호스트 프로세스·systemd)을 볼 수 없고, Caddy가 앱 컨테이너와 같은 네트워크에 묶인다. 설치형은 그 제약이 없다. 둘 다 같은 바이너리로 지원하고, 방식 분기는 조립(`app`) 한 곳에만 둔다. 설치형 꾸러미는 systemd 유닛과 설치 문서까지 (설치 스크립트는 만들지 않는다). M6보다 먼저 — 실서버 전환(M7)이 이것에 달려 있다. Docker 밖 프로세스 관리는 설치형에서만 되는 새 종류라 따로 설계한다.
10. **M6 정한 것** (2026-10-10) — 네 조각으로: M6-1 지켜보기·알림 → M6-2 로그 탭 → M6-3 진단·홈 "주의가 필요한 것" → M6-4 서비스 CPU·메모리.
11. **M7 정한 것** (2026-10-10) — 실서버는 **Docker 방식**으로 넘긴다 (v1과 같은 모양 — 전환·되돌리기가 compose 명령, 별칭이라 IP 바뀜 틈이 없다. 설치형은 Docker 밖 프로세스 종류를 만들 때). 인증서는 새로 받는다. 다섯 조각: M7-1 로컬(건너뛴 것 보고·운영 구성·전환 문서·가짜 실서버 리허설) → M7-2 실서버 조사(읽기만) → M7-3 그림자 실행 → M7-4 전환·되돌리기 리허설 → M7-5 7일 뒤 정리. 실서버에서 바꾸는 명령은 매번 확인을 받고 실행한다. 저장소 이름 변경은 M7 밖.
   멈춤은 두 번 연속(약 1분)일 때만. 외부 연결은 감시하지 않는다. 이 서버 IP는 관리 주소로 추정하고 `NARU_PUBLIC_IP`로 덮어쓴다.

### M4-1 — 인증서가 생기면 HTTPS로 넘기기

| 한 것 | 위치 |
|---|---|
| 인증서 읽기 — Caddy 저장소의 `.crt`만 읽어 덮는 이름·발급자·기간을 꺼낸다 (키는 열지 않는다) | `caddy.CertificateFiles` |
| 넘기기 판단 — HTTPS를 켠 주소에 지금 쓸 수 있는 인증서가 있을 때만 (관리 주소도 같은 규칙). 와일드카드는 한 단계 | `webserver.siteMapBuilder`, `model.Certificates.For` |
| 넘기기 그리기 — `:80`에서 `307`, 쿼리 유지, 인증서 확인 경로는 넘기지 않는다. 바깥 HTTPS 포트가 443이 아니면 `NARU_HTTPS_PORT` | `caddy.JSONWriter` |
| 화면 — 주소 옆에 "HTTPS · 12월 3일까지"(14일 안이면 노란색), 아직이면 "인증서 받는 중"과 DNS가 가리키는 곳. 설정의 관리 주소에도 | `views`, `web` |

새 이벤트는 없다 — 맞추기가 30초마다 지도를 다시 그리니, 인증서가 생기거나 끝나면 다음 맞추기에서 넘기기가 켜지고 꺼진다.
확인 (로컬, 내부 CA): `http://site.localhost/a/b?x=1` → `307 https://site.localhost:8443/a/b?x=1` · 확인 경로는 넘기지 않음 · HTTPS를 끈 주소는 HTTP 그대로 ·
인증서 폴더를 치우자 약 14초 뒤 넘기기 꺼짐, 되돌리자 약 30초 뒤 다시 켜짐 · 설정 골든을 실제 Caddy가 `validate`.

**아직 (M4-2):** 발급 실패 이유를 사람 말로 — 설계 노트 먼저.

### M5 — 서비스마다 웹서버 설정

| 한 것 | 위치 |
|---|---|
| 서비스 화면 "웹서버" 칸 — 점검 중 · 응답 헤더 · 허용 IP · 비밀번호 보호(기본 인증) · 경로별 연결 · 고급(Caddyfile). 칸마다 "nginx로 치면"을 함께 | `web/websettings.go`, `templates/service.html` |
| 한 요청이 지나가는 순서를 고정 — IP 제한 → 점검 중 → 비밀번호 → 헤더·압축 → 고급 → 경로 → 기본 목적지. 압축(zstd·gzip)은 늘 켬 | `caddy.site` |
| 인증서 확인 경로(`/.well-known/acme-challenge/*`)는 IP 제한·점검 중·비밀번호를 거치지 않는다 | `caddy.site` (테스트로 고정) |
| 고급 칸은 Caddy의 `/adapt`로 바꾸고, 그 사이트 안쪽 경로 처리만 꺼낸다 — TLS·관리·포트·다른 사이트는 버리고 알려 준다 | `caddy.AdaptCompiler` |
| 적용하면 바로 웹서버에 맞춰 보고, 거절되면 저장을 되돌린 뒤 웹서버가 한 말을 보여준다 | `websettings.webSettingsEditor` |
| 비밀번호는 bcrypt 해시만 저장·전송 (불변식 5의 예외로 문서화). 화면에는 "있음"만 | `websettings.BcryptHasher` |
| nginx에서 가져오기 — server 블록이나 NPM 고급 칸을 칸으로 옮겨 미리 보여주고, 옮기지 못한 줄은 줄 번호와 이유를 붙여 보여준다 (저장은 사람이) | `websettings.NginxReader` |
| 경로별 연결로 이 서비스에 보내는 다른 서비스를 대상 화면에 표시. 대상 서비스를 지우면 그 경로는 502 | `views`, `webserver.siteSettings` |

확인 (따로 띄운 검증 스택 · 진짜 Caddy · whoami 두 개): 비밀번호 없이 401 · 있으면 200과 `X-Test` 헤더 · `/api/hello`가 다른 서비스로 `GET /hello`(앞부분 뗌) ·
고급 칸 `respond /health 200` 동작 · 허용 밖 IP 403 · 그때도 인증서 확인 경로는 통과(200) · 점검 중 503 · 틀린 지시어는 Caddy의 말과 함께 400 ·
불러올 때만 드러나는 실패(없는 CA 파일)는 Caddy가 거절 → **Naru가 이전 설정으로 되돌림**, 다른 서비스는 영향 없음 · 큰 응답에 `content-encoding: gzip`.

### M5.5 — 설치 방식 두 가지 (Docker · 설치형)

| 한 것 | 위치 |
|---|---|
| `NARU_INSTALL=docker\|host` — 방식에 따른 기본값과 "웹서버가 닿는 방법"은 `app` 한 곳에서 고른다. 그 밖의 패키지는 방식을 모른다 (R12: 설정을 환경 변수에서 읽는 건 `app`뿐) | `app.modes` |
| 컨테이너 목적지 둘 — Docker는 별칭, 설치형은 컨테이너 IP. "이 서버"는 설치형에서 127.0.0.1로 그린다 (저장된 값은 그대로) | `kinds.ContainerAliasDestination` · `ContainerIPDestination` · `ExternalDestination` |
| 배포 순서를 바꿈 — 새 것 띄움 → 응답 확인(IP로) → 상태 저장 → **웹서버 맞춤** → 옛 것 내림. 맞추기가 실패하면 둘 다 남기고 다음 배포에서 정리 | `deploy.deployer`, `VersionSwapper.Retire` |
| 컨테이너 IP를 기록하고(`instance_ip`, 마이그레이션 005), 맞출 때마다 지금 IP로 덮어씀 — 재시작으로 바뀌어도 따라감 | `docker.Containers`, `webserver.siteMapBuilder` |
| 설치형은 앱 네트워크가 없으면 만든다 (dockerd 27은 없는 네트워크로도 create를 받고 start에서야 실패한다 — 먼저 확인) | `docker.Client.ensureNetwork` |
| 설치형은 Caddy 저장소를 데이터 폴더 안에 두도록 설정에 적는다 — Naru가 인증서를 읽는다 | `SiteMap.Storage` |
| 설치형 꾸러미 — systemd 유닛 둘(같은 `naru` 사용자, Caddy는 80·443 권한만), bootstrap 설정, 설치 문서 | `deploy/host/`, [설치형 설치](../install-host.md) |

확인 (Docker-in-Docker 리눅스 안에서 dockerd·caddy·naru를 호스트 프로세스로): 첫 설정 → 이미지 서비스 배포 → Caddy가 `172.19.0.2:80`(IP)로 보냄 ·
호스트 프로세스(`localhost:5000`)는 `127.0.0.1:5000`으로 · 관리 화면 `127.0.0.1:8080` · **다시 배포하는 동안 요청 6,154개 모두 200** ·
컨테이너 IP를 억지로 바꾸자(`.3`→`.4`) 26초 뒤 따라감.

**알아둘 것:** 설치형에서 컨테이너 IP가 바뀌면 다음 맞추기(최대 30초)까지 그 서비스 요청이 실패한다. Docker 방식은 이름으로 보내므로 이 틈이 없다.
재시작해도 Docker는 보통 같은 IP를 다시 주지만, 그 사이 다른 컨테이너가 IP를 가져가면 바뀐다. 줄이려면 Docker 이벤트를 듣고 바로 맞추면 된다 (설계 노트 필요).

가져오기: 계정 1 · 관리 주소 · 앱 2 · 주소 2 · 배포 기록 6, **옮기지 못한 것 0**. 인증서 셋 다 Let's Encrypt(HTTP 확인).

첫 비교에서 v1과 다른 곳 두 개 → 가져오기를 고침 (`c1874e5`):
- `potainer` 502 — 초기 v1 앱은 포트가 예전 칸(`port`)에만 있었다 → `coalesce(container_port, port)`, 그래도 비면 v1 호스트가 보내던 포트.
- `shelf` HTTPS 없음 — v1은 "인증서 사용"이 꺼져 있어도 덮는 인증서가 있으면 HTTPS로 서빙했다(SNI) → 덮던 이름이면 HTTPS를 켠다.

다시 띄운 그림자: 주소마다 HTTPS 응답이 크기까지 같다. 다른 것은 넘김 코드뿐(v1 301/302 ↔ v2 307/303).

# Caddy 사용성 분석

상태: 분석 · 2026-10-04
관련: [웹서버 엔진을 Caddy로 — 설계](caddy-engine.md)

---

## 0. 결론 먼저

> Caddy는 **처음 10분**이 압도적으로 좋고, **운영 몇 달**에서 막힌다.
> Shelf는 Caddy의 처음 10분을 그대로 지키고, 운영의 빈칸을 화면으로 메운다.

Caddy가 잘하는 것(기본값·짧은 설정·자동 HTTPS)은 **건드리지 않고 그대로 쓴다.**
Caddy가 못 하는 것(상태가 안 보임·원본이 둘·플러그인 재빌드·컨테이너를 모름)이 Shelf가 존재하는 이유다.

---

## 1. 어떻게 확인했나

Caddy v2.11.6 공식 이미지(`caddy:2`)로 사용자가 흔히 하는 작업을 직접 했다. 아래 표의 "실측"은 전부 이번에 돌려서 본 결과다.

| # | 해본 것 | 결과 |
|---|---|---|
| 1 | 흔한 설정(사이트 2개: 압축·헤더·IP 제한·비밀번호·프록시)을 Caddyfile로 작성 → JSON 변환 | **17줄 → 145줄**. 인증서 설정은 0줄인데 발급됨. 접근 로그는 꺼져 있음 |
| 2 | 지시어를 `reverse_proxy → redir → respond` 순서로 적음 | 실제 실행은 **`redir → respond → reverse_proxy`** |
| 3 | `reverse_proxi` 오타 | `Typo.caddyfile:2: unrecognized directive: reverse_proxi` — 파일·줄 정확, 대안 제시는 없음 |
| 4 | 기본 이미지의 DNS 제공자 플러그인 | **0개** (전체 모듈 135개) |
| 5 | 관리 API에 Caddyfile 조각을 보내 JSON으로 변환 (`POST /adapt`) | 동작함 |
| 6 | 관리 API로 설정 변경 → Caddyfile로 `reload` | **API 변경이 조용히 사라짐** |
| 7 | 관리 API로 볼 수 있는 것 | 설정 · 업스트림 상태 · Prometheus 지표 · 내부 CA는 있음. **인증서 목록은 없음** |
| 8 | 인증서 발급 진행 | 로그(`tls.obtain`)에만 나옴. API로는 알 수 없음 |
| 9 | 컨테이너 안에서 `localhost:2019`로 관리 API 접근 | **연결 거부** — Alpine에서 `localhost`가 `::1`로 풀리는데 관리 API는 `127.0.0.1`에만 열림 |
| — | (어제) 관리 설정이 빠진 JSON 적용 | 200으로 받아들임 → 제어 상실 → **재시작해도 회복 안 됨** |

이미지 크기는 23 MB다.

## 2. 잘하는 것 — 지켜야 할 것

### 2.1 기본값이 곧 정답이다

인증서 발급, HTTP→HTTPS 리다이렉트, HTTP/2·HTTP/3이 **아무것도 안 적어도** 켜진다. 실측 1에서 Caddyfile에 TLS 관련 내용이 한 줄도 없었는데 변환된 JSON에도 `tls` 블록이 없고, 실행하면 인증서를 받으러 간다.
Caddy가 유명해진 가장 큰 이유가 이것이다 — **안전한 설정이 노력 없이 기본으로 따라온다.**

### 2.2 짧고 읽힌다

```
blog.example.com {
	encode zstd gzip
	header -Server
	reverse_proxy blog:3000
}
```

같은 내용의 JSON은 8배 이상 길다(실측 1). Caddyfile은 사람이 쓰고, JSON은 기계가 쓴다.

### 2.3 틀린 곳을 정확히 짚는다

오타가 나면 **파일과 줄 번호**를 알려준다(실측 3). 설정 실수로 서버가 반쯤 뜨는 일이 없다.

### 2.4 자동화할 수 있게 열려 있다

관리 API가 설정 전체를 JSON으로 주고받고, **Caddyfile → JSON 변환까지 API로** 해준다(실측 5). 업스트림 상태와 지표도 API로 나온다(실측 7).

### 2.5 단순하다

단일 바이너리, 23 MB 이미지, 외부 의존성 없음.

## 3. 막히는 곳 — Shelf가 메워야 할 것

### 3.1 원본이 둘이 된다

Caddyfile로 시작해서 API로 고치면, 다음 `reload`에 API 변경이 **아무 경고 없이** 사라진다(실측 6). 운영하다 보면 누군가는 API를 쓰고 누군가는 파일을 고친다. 원본이 둘이 되는 순간 사고가 난다.

### 3.2 적은 순서대로 실행되지 않는다

Caddy는 지시어를 정해진 순서로 재배열한다(실측 2). 대부분은 알아서 맞게 되지만, 순서를 바꾸고 싶어지는 순간 `route`·`handle` 블록의 의미를 알아야 한다. Caddy 커뮤니티에서 가장 자주 나오는 질문 중 하나다.

### 3.3 인증서 상태가 안 보인다

"왜 https가 안 되지?"에 답하는 화면이 없다. 관리 API에 인증서 목록이 없고(실측 7), 발급 진행과 실패는 로그에만 남는다(실측 8). DNS가 아직 안 바뀌었는지, 80 포트가 막혔는지, Let's Encrypt 한도에 걸렸는지를 **로그를 뒤져서** 알아내야 한다.

### 3.4 플러그인은 다시 빌드해야 한다

기본 이미지에는 DNS 제공자가 하나도 없다(실측 4). 와일드카드 인증서 하나를 위해 `xcaddy`로 이미지를 직접 빌드하고, Caddy가 업데이트될 때마다 다시 빌드해야 한다.

### 3.5 관리 API가 위험할 만큼 쉽다

- 인증이 없다. 다른 컨테이너에서 닿으면 프록시 전체를 바꿀 수 있다.
- 관리 설정이 빠진 JSON 하나로 **영구히** 제어를 잃는다 (어제 실측).
- Docker 안에서는 `localhost`로 붙는 것부터 실패할 수 있다(실측 9).

### 3.6 컨테이너를 모른다

앱 컨테이너가 뜨고 지는 걸 Caddy는 모른다. 사람이 Caddyfile에 컨테이너 이름과 포트를 적고, 앱을 지우면 그 줄도 지워야 한다.

### 3.7 로그가 꺼져 있고, 켜도 읽기 어렵다

접근 로그는 기본으로 꺼져 있다(실측 1). 켜면 한 줄짜리 JSON이 쌓인다 — 기계에는 좋고 사람에게는 나쁘다.

### 3.8 헤더 문법은 짧은 대신 외워야 한다

`header -Server`, `header_up`, `header_down`, `+`/`-` 접두사, `{http.request.host}` 같은 자리표시자. 쓸 줄 알면 강력하고, 처음 보면 암호다.

## 4. 그래서 Shelf는 이렇게 한다

| Caddy에서 막히는 곳 | Shelf가 하는 일 |
|---|---|
| 원본이 둘 (3.1) | **Shelf DB만 원본.** Caddy에는 JSON을 통째로 밀어넣고 Caddyfile 파일은 두지 않는다 |
| 실행 순서 (3.2) | 화면에는 순서가 없다 — 켜고 끄기만. 실행 순서는 렌더러가 고정한다 (Caddy의 재배열과 같은 생각을 사용자에게 안 보이게) |
| 인증서가 안 보임 (3.3) | Caddy 저장소를 읽어 **도메인마다 상태**(발급됨 · 발급 중 · 실패 · 만료 임박)를 보여주고, `tls.obtain` 오류를 **사람 말로** 바꾼다 — "DNS가 이 서버를 가리키지 않습니다", "80 포트에 닿지 않습니다" |
| 플러그인 재빌드 (3.4) | 화면에서 필요한 플러그인(DuckDNS · Cloudflare …)을 고르면 **Shelf가 Caddy 이미지를 빌드한다.** Shelf는 이미 `docker build`를 하는 도구다 |
| 관리 API (3.5) | 유닉스 소켓으로만 열고, 관리 설정은 렌더러가 항상 그린다. 사용자는 API를 만질 일이 없다 |
| 컨테이너를 모름 (3.6) | 앱에 도메인을 적으면 연결되고, 앱을 지우면 같이 사라진다 (이미 있음) |
| 로그 (3.7) | 사이트별로 기본 켬. 화면에서 도메인·상태코드·시간으로 거른다 |
| 헤더 문법 (3.8) | 화면은 목록 입력. 그리고 고급 칸은 **Caddyfile 문법 그대로** 받는다 (아래) |

### 4.1 고급 칸은 Caddyfile로

설계 문서에서는 고급 칸에 Caddy JSON을 넣게 했는데, **Caddyfile로 바꾼다.** `POST /adapt`로 Caddy가 직접 JSON으로 바꿔주므로(실측 5) Shelf가 문법을 구현할 필요가 없다.

```
# 서비스 "blog"의 고급 설정 칸
header /assets/* Cache-Control "public, max-age=31536000"
@bot header User-Agent *bot*
respond @bot 403
```

- Caddy를 이미 아는 사람은 **그 지식을 그대로** 쓴다. 인터넷의 Caddyfile 예제를 붙여넣으면 된다.
- Shelf는 이 조각을 그 서비스의 블록 안에 넣어 `/adapt` → 나온 라우트만 그 서비스 자리에 끼운다. 다른 서비스나 전역 설정에는 닿지 않는다.
- `/adapt`가 거부하면 저장도 거부하고, Caddy의 오류 메시지(줄 번호 포함)를 그대로 보여준다.

화면 항목으로 만들 가치가 있는 것만 화면으로 만들고, 나머지는 Caddyfile에 맡긴다. 이것이 "Caddy를 잘 활용한다"의 구체적인 뜻이다.

## 5. 망치지 말아야 할 것

- **기본값을 뒤집지 않는다.** 자동 HTTPS는 기본, 끄는 쪽이 예외다. 화면이 체크박스 열 개를 내밀어 사용자가 고르게 만들면 Caddy의 장점이 사라진다.
- **Caddy를 고치지 않는다.** 공식 이미지(필요하면 플러그인만 더한 빌드)를 쓰고, Caddy 버전을 따라간다.
- **Caddyfile 지식이 통하게 한다.** Shelf 전용 문법을 새로 만들지 않는다.
- **가볍게 둔다.** Caddy 옆에 붙는 것은 Shelf 하나뿐이다.

## 6. 이미 있는 도구 사이에서의 위치

| 도구 | 하는 것 | 빈칸 |
|---|---|---|
| Caddy 단독 | 처음 10분이 최고 | 상태가 안 보임, 컨테이너를 모름, 원본 관리는 사람 몫 |
| caddy-docker-proxy | 컨테이너 레이블로 Caddyfile 자동 생성 | 화면·인증서 상태·알림 없음 |
| Nginx Proxy Manager | nginx 위에 화면 | GUI 수요를 증명했지만 엔진이 nginx라 Caddy의 기본값이 없음 |
| Coolify | 프록시(Traefik 기본, Caddy 선택) 위의 앱 플랫폼 | 범위가 넓고 무겁다 |

Shelf의 자리: **Caddy의 기본값 + 화면 + 앱 배포를, 서버 한 대 규모로 가볍게.**

## 7. 확인하지 못한 것

- **인증서 발급 실패 메시지의 실제 모양** — 발급 시도가 실패로 끝나기 전에 테스트 컨테이너를 지웠다. 오류를 사람 말로 바꾸려면 실서버(staging)에서 실패 사례를 모아야 한다.
- 잘못된 JSON을 `/load` 했을 때 이전 설정이 유지되는지 — 알려진 동작이지만 이번에 직접 보지는 않았다.
- HTTP/3 실사용 (UDP 443).

# 개발 프로세스 — 명세와 코드를 붙여두는 방법

문서가 코드와 어긋나면 문서가 아니라 거짓말이 된다. 그래서 어긋남을 **테스트로 잡는다**.

## 문서 네 개의 역할

| 문서 | 답하는 질문 | 언제 고치나 |
|---|---|---|
| [SPEC.md](SPEC.md) | **무엇을** 제공하는가 (F-번호) | 기능을 추가·삭제하기로 결정할 때 |
| [OBJECTS.md](OBJECTS.md) | **누가** 그 일을 하는가 (클래스별 한 문장) | 클래스를 만들기 **전에** |
| [ARCHITECTURE.md](ARCHITECTURE.md) | **어떤 모양으로** 쓰는가 (계층·패턴·규약) | 규칙을 바꿀 때 |
| [HISTORY.md](HISTORY.md) | **왜** 이렇게 됐는가 | 방향이 바뀌거나 실서버에서 교훈을 얻을 때 |

## 기능을 추가하는 순서

1. **SPEC에 항목을 적는다** — F-번호를 받고 상태를 ❌로 둔다. 여기 없는 기능은 만들지 않는다.
2. **OBJECTS에서 담당자를 고른다** — 기존 클래스로 설명되면 거기에, 안 되면 **새 문장을 먼저 쓴** 다음 클래스를 만든다.
3. 구현한다.
4. **테스트를 쓴다** — 단위(순수 로직) + 실제로 돌려본 결과. HTTP 200이 아니라 **결과물**을 확인한다.
5. `npm test`로 아키텍처 규칙까지 통과시킨다.
6. **SPEC 상태를 ✅로** 바꾼다. 미검증이면 ⚠️로 두고 무엇이 미검증인지 적는다.

## 자동으로 검사되는 것 (`core/tests/architecture.test.ts`)

`npm test`가 아래를 강제한다. 실패는 곧 "명세와 코드가 어긋났다"는 뜻이다.

| 검사 | 무엇을 막는가 |
|---|---|
| 시스템 간 import 금지 | auth/deploy/proxy가 서로를 직접 부르는 것 → EventBus로 |
| 날 SQL은 `db/`에만 | 도메인 코드에 SQL이 스며드는 것 |
| Hono 컨텍스트는 controller/kernel/middleware만 | HTTP 지식이 도메인·뷰로 퍼지는 것 |
| 뷰는 데이터 의존성 import 금지 | 화면이 스스로 DB·도커를 뒤지는 것 |
| 컨테이너 이름은 ContainerManager만 | `shelf-{앱}` 규칙이 여러 곳에 복제되는 것 |
| 모든 클래스가 OBJECTS에 존재 | 역할 문장 없는 클래스가 생기는 것 |
| 발행하는 이벤트가 OBJECTS에 선언됨 | 아무도 모르는 이벤트가 늘어나는 것 |
| SPEC의 F-번호 중복 없음 | 참조가 깨지는 것 |

## 검증 원칙 (실서버에서 배운 것)

- **상태코드가 아니라 결과물을 본다.** 200이어도 화면이 깨질 수 있다 (실제로 그랬다).
- **컨테이너로 돌려서 확인한다.** 로컬 dev 서버는 네트워크 위치가 달라 통과해도 실서버에서 깨진다.
- **이미지가 새 코드인지 먼저 확인한다.** 재빌드가 조용히 실패하면 아무리 고쳐도 옛 코드가 돈다.
  ```bash
  docker exec shelf grep -c <새로_추가한_식별자> /app/core/src/<경로>
  ```
- **미검증은 미검증이라고 적는다.** SPEC의 ⚠️는 "코드는 됐지만 실환경 확인 못 함"이다.

## 커밋 메시지

무엇을 왜 바꿨는지, 그리고 **어떻게 확인했는지** 남긴다. 버그 수정이면 원인을 한 문장으로.

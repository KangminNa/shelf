# 지금까지의 이력과 원래 의도

이 문서는 "왜 지금 이런 모양인가"를 남긴다. 코드에서 역추적하지 않아도 되도록.

## 1. 방향이 세 번 바뀌었다

Shelf는 처음부터 지금 모습이 아니었다. 큰 전환이 세 번 있었고, 각 전환의 이유가 현재 구조를 설명한다.

### 1기 — 모듈 프레임워크 (`5e2810a` ~ `2b08cc7` 이전)

**의도**: 모듈 개발자가 화면·기능·데이터만 작성하면 배포·DB·라우팅은 코어가 처리하는 프레임워크.

- 모듈 = `plugins/{name}/`에 `manifest.json` + `setup(ctx)` + 마이그레이션
- 코어가 모듈별 SQLite, 이벤트버스, 스케줄러, 스토리지, AI 등 12개 서비스를 주입
- 셸 자동 래핑, 라이브 프리뷰, GitHub에서 모듈 설치까지 구현

**왜 버렸나**: 모듈이 코어 프로세스 안에서 돌기 때문에 언어·DB·의존성이 코어에 묶였다. "내가 만든 모든 서비스를 올리고 싶다"는 목표에 이 제약이 정면으로 걸렸다.

### 2기 — 앱 = Docker 컨테이너 (`2b08cc7`)

**의도**: 실행 환경을 컨테이너에 맡겨 언어·프레임워크·DB를 완전히 자유롭게.

- 앱 계약이 **"저장소 루트에 Dockerfile, 컨테이너가 포트 하나로 HTTP 서빙"** 하나로 축소
- in-process 모듈 시스템(loader, plugins/, 미사용 서비스 6개, types.ts) 전부 제거
- Proxy/Deploy가 모듈이 아니라 **코어 내장 기능**으로 승격 (모듈은 삭제될 수 있지만 이 둘은 항상 있어야 함)

**남은 결과**: 코어 런타임 의존성이 3개(hono, @hono/node-server, better-sqlite3)로 줄었다.

### 3기 — 프록시가 컨테이너 네트워크로 (`a2cfb95` ~ `ca121a1`)

**의도**: 프록시가 앱에 도달하는 경로를 정상화.

2기까지는 앱을 호스트 포트에 publish하고 프록시가 `host.docker.internal`로 우회해서 접근했다. 실서버에서 이 우회가 세 가지로 터졌다:

1. 호스트 포트를 안 열면 도달 불가
2. `127.0.0.1`은 Shelf 컨테이너 자신을 가리킴
3. 컨테이너 이름은 네트워크가 달라 `EAI_AGAIN`

→ Shelf와 앱이 `shelf-net`을 공유하고 **컨테이너 이름으로 직접 연결**하도록 변경. 호스트 포트는 선택 항목이 됐다.

## 2. 실서버에서 드러난 문제들 (2026-08-17)

전부 "역할이 정의되지 않아 생긴 공백"이었다. 같은 실수를 반복하지 않기 위해 원인을 남긴다.

| 증상 | 진짜 원인 | 교훈 |
|---|---|---|
| 관리 화면에 HTML이 텍스트로 출력 | 엘리먼트 빌더 도입 후 문자열 템플릿 뷰가 이중 이스케이프. HTTP 200만 확인하고 **내용을 확인하지 않음** | 검증은 상태코드가 아니라 **결과물**로 |
| 프록시 502 (도달 불가) | 앱에 호스트 포트가 없으면 프록시가 닿을 수 없는 구조 | 연결 경로를 우회에 의존시키지 말 것 |
| `EAI_AGAIN` 반복 | 네트워크 공유가 없었고, 이후엔 **compose가 만들지 않은 네트워크** 때문에 컨테이너 교체가 조용히 실패 → 옛 이미지가 계속 실행 | 인프라 자원의 **소유자를 하나로** 정할 것 |
| 프록시 타깃을 매번 손으로 고침 | 프록시 호스트와 앱이 서로 몰라서, 앱을 지우거나 이름을 바꾸면 호스트가 고아가 됨 | 파생된 설정은 **소유자가 관리**하고 손으로 못 바꾸게 |
| Portainer `origin invalid` | 프록시가 업스트림에 Host를 target으로 덮어써서 앱의 Origin 검증이 실패 | 프록시는 **원 요청을 보존**해야 함 |
| `git pull` 충돌로 설정 유실 | 운영 설정이 `docker-compose.yml`에 직접 박혀 있었음 | 설정과 코드를 분리(`.env`) |

## 3. 우리가 하고 싶었던 것 (변하지 않은 목표)

방향은 세 번 바뀌었지만 목표는 처음부터 하나였다.

> **내가 만든 서비스들을 개인 서버에 쉽게 올리고, 도메인·SSL·CI/CD 같은 어려운 부분은 신경 쓰지 않는다.**

구체적으로:

1. **코드만 올리면 배포된다** — Vercel처럼. 빌드·실행·재시작을 손으로 하지 않는다
2. **도메인과 SSL이 자동** — Nginx Proxy Manager 수준의 관리를 UI에서
3. **push하면 반영된다** — 별도 CI 서버 없이 webhook으로
4. **서비스를 만드는 데 제약이 없다** — 언어·프레임워크·DB 자유
5. **혼자 운영할 수 있다** — 컨테이너 하나, 백업할 디렉토리 하나(`data/`)

## 4. 명시적으로 하지 않기로 한 것

범위를 지키기 위해 남긴다.

- **멀티 컨테이너 앱(docker-compose 저장소)** — 앱 하나 = 컨테이너 하나. DB가 필요하면 별도 앱으로 올려 환경변수로 연결
- **멀티 유저·권한 분리** — 관리자 계정은 서버 루트 권한과 동급이다(docker.sock). 나눠도 실질적 격리가 안 되므로 단일 관리자
- **오토스케일·클러스터** — 서버 한 대 전제
- **앱 런타임 대신하기** — 앱이 어떤 DB를 쓰든 Shelf는 모른다. 영속화는 볼륨으로
- **HTTP 아닌 프로토콜 프록시** — TCP/UDP 게임서버 등은 포트 직접 노출로만
